# ViewState 설계

화면은 로딩 중인지, 표시할 데이터가 있는지, 빈 결과인지, 오류가 발생했는지를 사용자에게 알려줘야 한다. 먼저 **한 시점의 화면이 어떤 상태를 표현할 수 있는지** 정한 뒤, 그 상태를 코드로 옮긴다.

## 서로 독립적이지 않은 값을 구분하기

`isLoading`, `posts`, `error`를 각각 관리하면 로딩 여부·데이터 유무·오류 유무만으로도 최대 여덟 조합이 생긴다. 첫 로딩, 내용 표시, 빈 결과, 로딩 실패처럼 의도한 조합도 있지만, 화면 정책이 정해지지 않은 조합도 만들어진다. 예를 들어 첫 로딩의 스피너와 치명적 오류를 동시에 표시해야 하는지는 명확하지 않다.

이 값들이 **하나의 화면 단계를 서로 다른 방식으로 표현하는 것**이라면, `loading`, `loaded(data)`, `empty`, `error(message)`처럼 서로 배타적인 상태로 묶는다. 데이터와 오류 메시지는 해당 상태의 연관 값으로 둔다. 그러면 화면은 존재할 수 있는 상태만 받아 `switch`로 각각의 표현을 선택할 수 있다.

## 화면 정책에 맞는 상태 만들기

- `empty`가 별도 화면을 보여준다면 독립된 상태로 둔다. 빈 목록도 일반 목록과 똑같이 표시한다면 `loaded([])`만으로 충분할 수 있다.
- 새로고침 중 기존 데이터를 계속 보여준다면 `loaded(data, isRefreshing: true)` 같은 조합은 유효하다. 이 경우 새로고침 여부를 내용 표시와 함께 모델링한다.
- 오래된 데이터를 보여주며 재시도 가능한 오류를 알리는 경우도 있다. 전체 화면을 대체하는 오류와 내용 위에 표시하는 오류를 구분한다.
- 시트 표시, 입력 중인 텍스트, 선택 상태처럼 화면 단계와 독립적으로 변하는 값은 별도의 상태로 둘 수 있다. 모든 UI 값을 하나의 거대한 enum에 넣지 않는다.

핵심은 상태 변수의 개수를 줄이는 것이 아니라, **실제로 가능한 조합만 표현하고 각 값의 소유 범위를 분명히 하는 것**이다.

## MVVM에서의 역할

ViewModel은 요청 결과와 사용자 이벤트를 화면 상태로 변환한다. View는 그 상태를 읽고 각 경우에 맞는 화면을 표시한다. SwiftUI에서는 프로젝트의 `@Observable` 모델을 View가 소유할 때 `@State`를 사용할 수 있다.

`enum`과 빠짐없는 `switch`는 정의하지 않은 **상태의 모양**을 만들거나 새 case의 화면 처리를 누락하는 일을 줄인다. 다만 로딩에서 성공·빈 결과·오류로 올바르게 전이하는지, 재시도나 동시 요청 결과를 어떻게 처리하는지는 별도로 검증해야 한다. ViewModel의 상태 전이는 View를 띄우지 않고 테스트할 수 있다.

구체적인 코드와 상태 전이 예시는 [ViewState 예시](view-state/examples.md)를 참고한다.
