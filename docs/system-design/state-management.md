# 상태 관리

상태는 화면에 필요한 현재의 값이다. 상태를 어디에 둘지는 값의 종류보다 **수명, 원본 위치, 소유 범위**를 먼저 보고 결정한다.

## 모든 상태를 한곳에 모으면 생기는 문제

성격이 다른 상태를 하나의 큰 객체에 모으면 처음에는 접근하기 쉽다. 그러나 기능이 늘수록 서로 다른 변경과 수명주기가 결합된다.

- **불필요한 UI 작업:** 작은 변경이 넓은 범위의 상태를 사용하는 화면에 영향을 줄 수 있다. 실제 재계산 범위는 UI 기술의 관찰 방식과 화면이 읽는 값에 따라 달라지지만, 관련 없는 상태가 함께 묶일수록 변경의 영향을 예측하기 어려워진다.
- **불분명한 수명과 저장 정책:** 일시적인 입력값, 여러 화면에서 공유하는 값, 서버 데이터의 사본, 디스크에 남겨야 하는 값을 같은 수명으로 다루기 어렵다.
- **커지는 테스트 준비:** 한 동작을 검증하는 데 관계없는 세션, 데이터, 외부 응답까지 준비해야 할 수 있다.

따라서 상태를 무조건 작게 나누기보다, **같은 이유로 변경되고 같은 범위에서 유지되는 값**을 함께 둔다.

## 상태를 보는 네 가지 관점

| 관점 | 의미 | 예시 | 주로 살펴볼 점 |
|------|------|------|------|
| UI State | 화면 또는 구성 요소의 표현·상호작용 상태 | 입력 중인 텍스트, 시트 표시 여부, 애니메이션 진행률 | 어느 화면에서 생성되고 언제 사라지는가 |
| Domain State | 사용자의 작업과 비즈니스 규칙에 필요한 상태 | 장바구니, 로그인 세션, 작성 중인 글 | 여러 화면에서 공유해야 하는가 |
| Server State | 서버가 최종 원본을 가진 데이터의 로컬 사본 | 피드, 다른 사용자의 프로필, 좋아요 수 | 언제 갱신하고 서버와 어떻게 동기화하는가 |
| Persistent State | 앱을 종료한 뒤에도 유지해야 하는 상태 | 인증 정보, 사용자 설정, 작성 중인 글의 초안 | 무엇을 어디에 저장하고 언제 복원하는가 |

이 구분은 서로 배타적이지 않다. 예를 들어 작성 중인 글은 Domain State이면서 디스크에 저장할 수 있고, 서버에서 받은 피드는 Server State이면서 화면 간에 공유할 수 있다. **Persistent State는 특히 저장 필요성을 나타내는 속성**으로 볼 수 있다.

## 상태의 위치를 정하는 질문

1. **얼마나 오래 유지해야 하는가?** 구성 요소, 화면, 여러 화면, 앱 세션, 앱 재시작 이후 중 어디까지 필요한가?
2. **최종 원본은 어디에 있는가?** 사용자 입력, 앱 내부, 서버 중 무엇이 이 값을 결정하는가?
3. **디스크 저장이 필요한가?** 종료 후 복원이 필요한 값과 다시 가져오거나 계산할 수 있는 값을 구분한다.
4. **누가 읽고 변경하는가?** 필요한 범위가 넓어질 때에만 소유 범위를 넓힌다.

여러 화면에서 같은 데이터의 기준을 유지하는 방법은 [데이터 플로우와 SSOT](ssot.md)를 참고한다.
