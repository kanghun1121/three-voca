# 데이터 플로우와 SSOT

같은 게시물이 홈과 프로필에 표시된다고 가정하자. 홈에서 좋아요를 눌렀는데 프로필의 하트는 비어 있다면, 두 화면이 같은 데이터의 서로 다른 사본을 기준으로 표시하고 있는 것이다. 화면마다 사본을 독립적으로 관리하면 한곳의 변경을 다른 곳에 전파하고 동기화해야 한다.

**SSOT(Single Source of Truth)는 어떤 값을 기준으로 사용할지 명확히 정하는 원칙**이다. 데이터를 물리적으로 한곳에만 저장해야 한다는 뜻은 아니다. 서버가 원본인 데이터를 로컬 DB에 저장하거나 화면용으로 가공할 수 있다. 다만 각 사본이 무엇을 기준으로 갱신되는지 정해져 있어야 한다.

## 여러 화면에서 공유하기

여러 화면에 필요한 데이터는 특정 화면이 다른 화면에 변경을 알리는 방식보다, 화면 바깥의 공통 데이터 소스를 통해 제공한다. 각 화면은 필요한 값을 구독하거나 조회하고, 변경이 있으면 같은 기준에서 새 값을 받는다. 공통 데이터 소스는 데이터의 성격에 따라 Repository, Store, Cache 등으로 구성할 수 있으며, 앱 전체를 하나의 거대한 상태 객체로 만들 필요는 없다.

화면에만 필요한 선택 상태나 애니메이션 상태까지 공유하지 않는다. **공유 범위는 그 값을 실제로 함께 사용하는 범위**로 제한한다.

## 변경을 한 방향으로 흐르게 하기

읽는 곳이 같더라도 여러 화면이 공유 값을 임의로 수정하면 변경 이유를 추적하기 어렵다. 화면은 사용자 이벤트를 변경 요청으로 전달하고, 데이터 소유자가 값을 갱신한 뒤 새로운 상태를 제공한다.

```text
사용자 이벤트 → 화면 → 변경 요청 → 데이터 소유자 → 새 상태 → 해당 데이터를 읽는 화면들
                                  ↕
                            외부 원본과 동기화
```

이 흐름에서 화면은 다른 화면의 상태를 직접 수정하지 않는다. 서버가 원본이라면 요청 결과나 외부 변경을 데이터 소유자가 반영하고, 각 화면은 그 결과를 읽는다.

## 예: 좋아요의 낙관적 업데이트

게시물의 좋아요 정보는 서버가 최종 원본을 가진다. 사용자가 버튼을 누른 직후 서버 응답보다 먼저 하트를 채울 수 있다. 이는 서버 데이터의 **로컬 사본을 먼저 변경**하고, 요청 결과에 맞춰 동기화하는 낙관적 업데이트다.

이때 화면에 보이는 값과 서버에 확정된 값을 구분해야 한다. 요청이 실패하면 표시를 되돌리거나 서버 값을 다시 가져오는 등 정합성을 회복할 방법이 필요하다. 즉, 즉각적인 UI 반응이 데이터의 최종 소유 위치를 바꾸지는 않는다.

서버 데이터의 사본을 얼마나 오래 사용할지는 [캐시 제어](cache-control.md)에서 다룬다.
