# 서버 통신 실패와 복구

사용자가 요청을 보낸 뒤 타임아웃을 보았다고 해서 서버가 작업을 처리하지 않았다고 단정할 수 없다. 요청이 서버에 도착해 처리됐지만 응답만 유실되었을 수도 있다. **클라이언트가 확실히 아는 것은 정상 응답을 받지 못했다는 사실**이며, 중요한 작업일수록 이 불확실성을 화면과 데이터 흐름에 반영해야 한다.

## 요청이 끊길 수 있는 지점

```text
입력 → 로컬 보존 → 요청 시작 → 서버 처리 → 응답 수신 → 완료 표시
          │              │           │            │
          └ 저장 실패     └ 전송 실패  └ 결과 불명  └ 표시·저장 실패
```

| 지점 | 클라이언트가 확인할 수 있는 것 | 대응 |
|---|---|---|
| 로컬 보존 전 | 앱이 종료되면 입력을 잃을 수 있다. | 복구가 필요한 입력은 요청 전에 로컬에 보존한다. 저장 실패도 사용자에게 드러낸다. |
| 요청을 시작하기 전 | 요청을 아직 보내지 않았다면 서버 작업은 시작되지 않았다. | 저장된 입력으로 다시 시도할 수 있다. |
| 요청 시작 후 응답을 받기 전 | 타임아웃·연결 끊김만으로 서버 처리 여부를 알 수 없다. | 작업 상태를 확인하거나, 서버가 중복 처리를 막는 같은 작업 식별자로 재시도한다. |
| 응답을 받은 뒤 완료 표시 전 | 처리 결과를 알고 있어도 앱의 로컬 기록·화면 반영이 끝나지 않을 수 있다. | 재진입 시 서버 결과와 로컬 기록을 대조해 완료 표시를 복원한다. |

전송이 시작된 뒤에는 오류가 발생한 정확한 위치를 클라이언트가 항상 구별할 수 없다. 위 표는 **실패 가능 지점과 복구 방법**을 나눈 것이며, 네트워크 오류만으로 어느 지점에서 멈췄는지 판정하는 절차는 아니다.

## 중복 실행을 막는 작업 식별

결제, 주문 생성, 제출처럼 한 번만 실행돼야 하는 동작은 같은 의도를 다시 보냈을 때 서버가 중복 실행을 막을 수 있어야 한다. 클라이언트는 작업을 시작할 때 고유한 식별자(예: idempotency key)를 만들고, **같은 작업의 재시도에는 같은 식별자**를 사용한다. 새로운 결제 의도에는 새 식별자를 사용한다. 앱 재시작 뒤에도 재시도해야 한다면 식별자와 작업 상태를 함께 보존한다.

식별자만 보내는 것으로는 충분하지 않다. 서버가 식별자와 요청 내용을 검증하고, 이미 처리한 작업의 결과를 다시 돌려주거나 그 상태를 조회할 수 있어야 한다. 결제처럼 결과의 영향이 큰 작업은 결과가 불명확할 때 새 요청을 만들기 전에 서버의 작업 상태를 확인한다. 서버가 중복 방지나 결과 조회를 제공하지 않는다면 클라이언트만으로 안전한 자동 재시도를 보장할 수 없다.

## 재시도 가능한 요청 구분하기

조회처럼 반복해도 결과가 중복 생성되지 않는 요청과, 중복 방지 계약이 있는 쓰기 요청을 구분한다. 타임아웃, 일시적인 서버 오류, 요청 제한은 재시도 후보가 될 수 있지만 입력 오류처럼 다시 보내도 바뀌지 않는 실패는 즉시 알려준다. 응답 코드만으로 처리 여부가 확정되지 않는 API는 서버 계약을 확인한다.

## 재시도 간격과 전체 횟수 정하기

재시도할수록 대기 시간을 늘리고 최대 횟수 또는 전체 대기 시간을 제한한다. 서버가 재시도 시점을 알려주면 이를 고려한다.

여러 클라이언트가 같은 간격으로 재시도하면 복구 중인 서버에 요청이 다시 몰릴 수 있다. 대기 시간에 작은 무작위 차이(jitter)를 둔다. 네트워크 계층과 기능 계층이 각각 재시도하는지도 확인해 시도 횟수가 의도치 않게 늘어나지 않도록 한다.

## 사용자 중복 조작 다루기

요청 진행 중 버튼을 비활성화하는 것은 연속 탭을 줄이는 UI 장치다. 앱 재실행이나 네트워크 재전송까지 막지는 못하므로 서버의 중복 방지와 별도로 생각한다.

## 모바일에서 입력을 보존하기

작성 중인 글이나 긴 폼처럼 다시 입력하기 어려운 값은 화면 메모리에만 두지 않는다. 사용자의 입력을 적절한 시점에 로컬 초안으로 저장하고, 앱 재실행 후 복원할 수 있게 한다. 제출할 때는 **초안 저장 성공**과 **서버 처리 완료**를 다른 단계로 취급한다. 로컬에 저장되었다는 이유만으로 서버에 반영되었다고 표시하지 않는다.

오프라인 제출이나 앱 재시작 후 재시도가 필요한 기능이라면, 보낼 내용·작업 식별자·현재 단계를 로컬에 보존하는 방식을 검토한다. 재시도 전에 서버 상태를 확인하고, 완료가 확인되면 로컬 대기 기록을 정리한다. 반대로 짧고 다시 만들기 쉬운 입력에까지 지속 저장과 자동 재시도를 적용할 필요는 없다. 민감한 입력은 로컬 저장 여부와 보관 기간을 별도로 결정한다.

## 화면에서 결과를 표현하기

서버 처리 결과를 모를 때에는 단순히 `실패`라고 확정하지 않는다. `처리 중`, `완료`, `입력 수정 필요`, `결과 확인 필요`처럼 사용자가 다음 행동을 판단할 수 있는 상태를 구분한다. 특히 금전 거래에서는 결과 확인이 끝나기 전에 새 결제를 유도하지 않는다.

## 설계할 때 확인할 것

1. 같은 요청이 두 번 실행되면 실제로 어떤 문제가 생기는가?
2. 응답이 오지 않았을 때 서버 결과를 어떤 식별자로 조회할 수 있는가?
3. 같은 작업의 재시도를 서버가 어떻게 중복 처리 없이 받아들이는가?
4. 사용자 입력을 언제 저장하고, 저장 실패·앱 재시작 후 어떻게 복원하는가?
5. 재시도 조건·간격·횟수와 사용자에게 보여줄 상태는 무엇인가?
