# 캐시 제어

캐시는 원본 데이터의 사본이다. 사본을 받은 직후에는 원본과 같더라도, 이후 원본이 바뀌면 캐시가 자동으로 갱신되지는 않는다. 삭제된 게시물이 피드에 남거나, 다른 화면에서 이미 바뀐 값이 예전 값으로 보이면 사용자에게는 버그처럼 느껴질 수 있다.

캐시 정책의 핵심은 **어떤 데이터를 얼마나 오래된 상태로 보여줘도 되는지** 결정하는 것이다. 모든 데이터에 맞는 단일 TTL이나 갱신 방법은 없다. 데이터의 중요도와 변경 빈도, 네트워크 비용, 오래된 값을 보여줄 때의 영향을 함께 본다.

## 만료와 무효화

| 방식 | 의미 | 적용할 상황 |
|------|------|------|
| 만료(Expiration) | 저장한 시점 또는 마지막 검증 시점부터 일정 시간이 지나면 더 이상 최신이라고 간주하지 않는다. | 변경 사실을 직접 알기 어렵고, 일정 기간의 오래된 값이 허용될 때 |
| 무효화(Invalidation) | 시간이 남았더라도 특정 사건 이후 기존 값을 더는 신뢰하지 않도록 한다. | 사용자가 값을 수정하거나 삭제했을 때, 로그아웃했을 때 등 |

TTL(Time to Live)은 캐시를 최신으로 취급하는 시간 기준이다. 예를 들어 피드의 TTL이 남아 있어도 사용자가 게시물을 삭제했다면 관련 캐시를 즉시 무효화할 수 있다. 반대로 TTL이 지났다고 저장된 사본을 반드시 삭제해야 하는 것은 아니다. **재검증을 기다리는 동안 보여줄 수 있는지**를 별도로 정한다.

## 원본과 다시 맞추기

원본의 변경을 알거나 확인하는 경로는 크게 두 가지다.

1. **클라이언트가 다시 확인한다.** 화면 재진입, 새로고침, TTL 만료 등 정해진 시점에 서버에 재요청한다.
2. **서버가 변경 신호를 보낸다.** APNs 같은 푸시 알림이나 실시간 연결을 받은 뒤 관련 데이터를 다시 읽거나 무효화한다. 백그라운드 푸시는 전달이 보장되지 않으므로, 이것만으로 최신 상태를 보장하지 않는다.

오래된 값이 잠시 허용된다면 캐시를 먼저 보여주고 백그라운드에서 재검증할 수 있다. 이때 **최신으로 취급할 기간**과 **오래된 값을 표시할 수 있는 최대 기간**을 구분한다. 오래된 값이 허용되지 않는 데이터라면 재검증 결과를 기다리거나 사용 가능한 상태가 아님을 보여준다.

## 조건부 재검증

서버가 `ETag`를 제공한다면 클라이언트는 저장한 태그를 `If-None-Match`와 함께 보내 변경 여부를 확인할 수 있다. 서버가 `304 Not Modified`를 반환하면 기존 본문을 계속 사용하고 검증 시점을 갱신한다. 새 본문이 오면 캐시를 교체하고, 삭제가 확인되면 해당 사본을 제거한다.

조건부 재검증은 **변경되지 않은 본문의 재전송을 줄이는 방법**이다. 서버에 확인 요청을 보내는 횟수 자체가 없어지는 것은 아니다.

## 동시 만료와 요청 집중

인기 있는 데이터의 사본들이 비슷한 시각에 만료되거나, 많은 클라이언트가 같은 사건 직후 재요청하면 원본 서버에 요청이 몰릴 수 있다. 이런 상황에서는 만료 시점에 작은 무작위 차이(jitter)를 두거나, 같은 키의 동시 재요청을 합치고, 실패 후 재시도 간격을 분산할 수 있다. 필요한 조치는 캐시가 놓인 위치와 실제 트래픽에 맞춰 선택한다.

## 정책을 정할 때 확인할 것

- 최신 값이 필요한 시점과 오래된 값을 허용할 수 있는 최대 시간은 무엇인가?
- 수정·삭제·로그아웃 같은 사건에서 어떤 캐시를 무효화해야 하는가?
- 재검증 실패 시 기존 값을 보여줄 것인가, 오류를 보여줄 것인가?
- 같은 데이터를 읽는 화면들이 [동일한 기준](ssot.md)에서 갱신되는가?
