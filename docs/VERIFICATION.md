# VERIFICATION.md

> 가장 위험한 순간은 Claude가 틀렸음에도 그럴듯하게 완료됐다 하는 경우.

검증은 테스트 실행이 아니다. **테스트가 무엇을 보장하고, 무엇을 보장하지 않는지**까지 보는 것이다.  
이 문서를 따르지 않으면 검증을 완료한 것으로 보고하지 않는다.

---

## Layer 1 — 자동 검증

반복 가능한 도구로 실행한다. 하나라도 실패하면 Layer 2, 3로 넘어가지 않는다.

```
[ ] build_sim 성공 (error 0개)
[ ] test_sim 전체 통과
[ ] swift-lint 위반 없음
```

자동 검증이 통과한 뒤, 다음 두 가지를 반드시 명시한다:

- **테스트가 보장하는 것**: 현재 테스트가 커버하는 시나리오
- **테스트가 보장하지 않는 것**: 커버되지 않는 시나리오 (이것이 더 중요하다)

---

## Layer 2 — 구조 검증

변경 사항을 리뷰한다. `git diff`를 직접 읽는다.

### 범위 검사

```bash
git diff --stat HEAD  # 변경된 파일 목록과 줄 수
```

- exec-plans/active/ 의 계획서와 비교한다
- 계획에 없는 파일이 변경됐는가?
- 계획에 없는 기능이 추가됐는가?
- 요청 범위를 벗어난 리팩토링이 포함됐는가?

**범위 초과 변경이 발견되면**: 해당 변경을 롤백하거나 별도 작업으로 분리한다. 하나의 PR에 섞지 않는다.

### 공개 API 검사

- `public`, `open` 키워드가 붙은 타입/함수가 변경됐는가?
- Interface 타겟의 파일이 변경됐는가? (`FeatureXxxInterface`, `DomainInterface`)
- 변경됐다면: 해당 Interface를 참조하는 다른 모듈에 영향이 없는가?

### 컨벤션 검사

- 3-Layer 데이터 모델 방향을 따르는가? (Entity → Domain → ViewState, 역방향 없음)
- 새 파일이 올바른 레이어/타겟에 위치하는가?
- 기존 코드 스타일과 일관성이 있는가?

---

## Layer 3 — 반례 검증

변경된 코드를 읽고 빠진 케이스를 찾는다. 도구 없이 추론한다.

### 엣지 케이스

변경된 함수마다 다음을 확인한다:
- 빈 배열 / nil / 0이 들어오면?
- 최대값 / 최소값 경계에서?
- 네트워크 실패 / 타임아웃이 발생하면?

### Race Condition

`async`/`await` 또는 `@MainActor` 가 포함된 변경이라면:
- 동시에 두 번 호출되면?
- 뷰가 사라지는 도중 응답이 오면?
- Task가 취소되는 시점에서?

### 잘못된 입력

- 사용자가 예상치 못한 값을 입력하면?
- API 응답이 예상 스키마와 다르면?

```

- 빌드: PASS
- 테스트: PASS (n개)
- 린트: PASS

보장하는 것: ...
보장하지 않는 것: ...

### Layer 2 — 구조 검증
- 범위: 계획 내 / 계획 초과 (초과 시 상세 내용)
- 공개 API 변경: 없음 / 있음 (있을 시 상세 내용)
- 컨벤션: 준수

### Layer 3 — 반례 검증
- 확인한 엣지 케이스: ...
- 미커버 리스크: ...

### 판정
PASS → PR 생성 가능
FAIL → [원인] 계획 단계부터 재시작
```
