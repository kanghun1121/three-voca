# swift-lint

POSTECH Apple Developer Academy Swift Style Guide + 사용자 커스텀 룰 기반 Swift 코드 린터.

## 참조 룰 파일

검토 대상에 따라 필요한 파일만 읽는다 (모두 읽을 필요 없음):

| 파일 | 다루는 카테고리 | 언제 읽나 |
|------|----------------|----------|
| `references/naming-rules.md` | 변수/함수/enum/struct/class/protocol/delegate 네이밍 | 거의 항상 |
| `references/format-rules.md` | 들여쓰기, 띄어쓰기, **파라미터 줄바꿈**, **import 정렬**, 주석 | 거의 항상 |
| `references/code-rules.md` | 클로저, 타입 추론/어노테이션, 메모리 관리 | 함수/타입 다룰 때 |
| `references/swiftui-rules.md` | SwiftUI View 선언 방법, 레이아웃 컨테이너 | SwiftUI 코드일 때 |

## 사용자 커스텀 룰 (강조)

POSTECH 가이드에 더해 본 프로젝트는 다음 2개를 추가한다:

1. **파라미터 3개 이상일 때만 줄바꿈** — 1~2개는 한 줄, 3개 이상은 한 줄에 하나씩.
2. **Import 그룹 순서 + 알파벳 정렬** — Apple Framework → Module(내부) → Third Party(외부) 순으로 그룹을 나누고, 각 그룹 안에서 알파벳 오름차순. 그룹 사이 빈 줄 1개.

상세는 `references/format-rules.md` §파라미터 줄바꿈 / §Import 정렬 참조.

## 트리거 케이스 vs 비-트리거 케이스

### ✅ 이 스킬을 사용한다

- "이 Swift 코드 린트해줘"
- "스타일 가이드대로인지 봐줘"
- "코드 리뷰해줘" (Swift 파일 맥락에서)
- "컨벤션 체크"
- "이 함수 스타일 어때?"
- "review this Swift code"
- "lint check please"
- Swift 파일이 첨부된 상태에서 "이거 괜찮아?", "문제 있어?"

### ❌ 이 스킬을 사용하지 않는다

- "이 기능 구현해줘" → 코드 작성 작업
- "버그 고쳐줘" → 디버깅
- "성능 최적화" → 별도 분석
- "테스트 코드 짜줘" → 코드 작성
- 비-Swift 코드 검토 요청

## 작업 워크플로우 (5단계)

### 단계 1 — 검토 대상 파악

다음을 결정한다:
- 단일 파일인가, 여러 파일인가?
- 파일에 SwiftUI View가 있는가? (있으면 swiftui-rules.md 로드)
- 함수/메서드가 많은가? (있으면 code-rules.md 로드)
- 전체 검토인가, 특정 부분만인가?

### 단계 2 — 룰 파일 선택적 로드

대상 코드의 성격에 따라:

| 파일 종류 | 로드할 룰 |
|-----------|----------|
| 일반 Swift 코드 (함수/클래스/struct) | naming + format + code |
| SwiftUI View 코드 | naming + format + code + swiftui |
| 모델/DTO만 있는 파일 | naming + format |
| Test 코드 | naming + format + code |

판단 어려우면 4개 모두 로드해도 무방.

### 단계 3 — 카테고리별 체크

대상 코드를 위에서 아래로 한 번 훑으면서 카테고리별 위반을 수집한다.

체크 순서:
1. **Import 섹션** — 알파벳 순서 / 중복 / 줄바꿈 위치
2. **타입 선언부** — 네이밍 (struct/class/enum/protocol)
3. **프로퍼티** — 네이밍, 타입 어노테이션, computed/observer 위치
4. **이니셜라이저** — 파라미터 줄바꿈 (커스텀 룰)
5. **함수/메서드** — 네이밍, 파라미터 줄바꿈, 클로저 사용
6. **클로저 호출** — 후행 클로저 축약, 다중 클로저 형식
7. **주석** — `///` 사용, MARK/TODO/FIXME
8. **들여쓰기/띄어쓰기** — 4 스페이스, 콜론 띄어쓰기
9. **SwiftUI 한정** — Struct로 View 선언, 레이아웃 컨테이너 1개
10. **메모리** — weak/unowned, Optional weak

각 위반은 다음 정보를 수집:
- 위치 (라인 번호 또는 함수/타입 이름)
- 현재 코드 (Bad)
- 수정 코드 (Good)
- 룰 카테고리 + 룰 이름
- 우선순위 (P0/P1/P2)

### 단계 4 — 위반 사항 보고

다음 형식으로 보고한다.

#### 보고 템플릿

```markdown
# Swift Lint 결과

**파일**: `<파일경로>`
**총 위반 건수**: N건 (P0: x, P1: y, P2: z)

---

## P0 — 강제 사항 (즉시 수정 권장)

### 1. [<카테고리>] <룰 이름>
**위치**: 라인 X (또는 함수 `funcName`)

**현재 (Bad ❌)**:
\`\`\`swift
<위반 코드>
\`\`\`

**수정 (Good ✅)**:
\`\`\`swift
<수정 코드>
\`\`\`

**근거**: `references/<file>.md` §<섹션>

---

## P1 — 권장 사항
... (P0와 동일 형식)

## P2 — 선호 사항
... (간단히 한 줄로 나열)

---

## 요약
- ✅ 잘 따르고 있는 룰: <간단히>
- ⚠️ 가장 많이 어긴 카테고리: <카테고리명>
- 💡 다음 작업 추천: <한 줄>
```

#### 우선순위 기준

| 등급 | 의미 | 예시 |
|------|------|------|
| **P0** | 명백한 위반. 컴파일/협업에 직접 영향 | UpperCamelCase 위반, 함수 prefix, weak 미사용으로 retain cycle 의심 |
| **P1** | 컨벤션 위반. 가독성/일관성 문제 | 파라미터 3개+ 한 줄, import 정렬 위반, 콜론 띄어쓰기 |
| **P2** | 선호 사항. 의견 차이 가능 | 타입 추론 vs 어노테이션, MARK 추가 권장 |

### 단계 5 — 자동 수정 제안 (선택)

사용자가 "수정해줘", "고쳐줘"라고 하면:

1. **P0/P1만 자동 수정 적용**. P2는 사용자 결정.
2. 파일을 읽고 위반 사항을 한 번에 모두 수정한다.
3. 수정 전후 diff를 보여준다.
4. 사용자가 일부만 수정하길 원하면 위반 ID를 명시하게 한다 ("1번, 3번만 수정").

수정 시 주의:
- **로직 변경 절대 금지**. 스타일만.
- 변수명 바꾸면 사용처 모두 같이 바꿔야 함 (책임지고 처리).
- 의심스러우면 사용자에게 확인.

## 검토 시 자주 빠지는 함정

| 함정 | 방지법 |
|------|--------|
| Import 그룹 순서를 틀림 (Third Party를 Module보다 앞에 배치) | Apple Framework → Module(내부) → Third Party(외부) 순서를 반드시 지킨다 |
| 파라미터 줄바꿈 룰을 함수 호출에만 적용 | 함수 선언/호출/이니셜라이저 모두 동일 적용 |
| `get` 함수를 모두 `fetch`로 바꿈 | 비동기/실패 가능 → `request`, 즉시 반환 → `fetch`. 구분해서 제안 |
| Bool 변수 이름 검증 누락 | `isXxx`, `hasXxx`, `shouldXxx` 형태 권장 (가이드에 명시 안 됐어도 일반적) |
| weak 검토 시 모든 weak 타입을 Optional 강제 | 가이드 룰. 단 사용 맥락 본 후 제안 |
| 클로저 축약을 항상 강제 | 단일 후행만 축약. 다중일 땐 라벨 유지 |
| SwiftUI 룰을 UIKit 코드에 적용 | 파일 맥락 먼저 확인 |

## 사용 예시

### 예시 1 — 단일 파일 린트

**사용자**: (Settings.swift 첨부) "이 코드 린트해줘"

스킬 동작:
1. 파일을 view로 읽음.
2. SwiftUI View 있으면 swiftui-rules.md 로드, 외에는 naming/format/code 로드.
3. 위에서 아래로 카테고리별 체크.
4. 위반 수집 → P0/P1/P2 분류.
5. 보고 템플릿 형식으로 결과 제시.
6. 마지막에 "수정도 적용할까요?" 한 번 물음.

### 예시 2 — 막연한 평가 요청

**사용자**: (코드 첨부) "이거 어때?"

스킬 동작:
1. Swift 코드면 린트 스킬 트리거.
2. "스타일 관점에서 검토해 드리겠습니다"라고 명시 후 진행.
3. 단계 3~4 진행.
4. 단, 위반이 0건이면 "스타일 위반은 없습니다. 다른 측면(성능/테스트성)도 봐드릴까요?" 추가.

### 예시 3 — 특정 룰만 검토

**사용자**: "Import 정렬만 봐줘"

스킬 동작:
1. format-rules.md만 로드.
2. Import 섹션만 검토.
3. 다른 카테고리는 건너뜀.
4. 보고도 import 위반에 집중.

### 예시 4 — 자동 수정

**사용자**: "린트 결과 P0/P1 다 고쳐줘"

스킬 동작:
1. 직전 린트 결과 참조 (없으면 다시 린트).
2. str_replace 또는 create_file로 수정 적용.
3. 수정된 파일을 사용자에게 제시.
4. 변경 사항 요약 (어떤 카테고리에서 몇 건 수정했는지).

## 의문이 들면

룰 파일을 다시 읽는다. 카테고리별로 잘 분리되어 있어 빠르게 찾을 수 있다.
모호한 케이스는 **위반으로 단정하지 않고 P2로 제안**한다 — 가이드도 "취향에 문제가 많기 때문에"라고 명시한다.

스타일 가이드의 목적은 **싸우지 않고 코드 읽기 좋게 하는 것**이다. 너무 엄격하게 굴어 사용자를 피곤하게 하지 말 것.
