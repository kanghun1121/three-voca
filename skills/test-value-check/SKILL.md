# Test Value Check

테스트 개수나 커버리지 수치보다 **잘못된 동작을 발견할 수 있는지**를 판단한다. 아래 체크박스는 검토 후보이며, 모든 테스트에 모두 적용하는 규칙이 아니다. 테스트를 더 쓰는 제안과 가치가 낮은 테스트를 합치거나 제거하는 제안을 함께 검토한다.

## 검토 방법

테스트 이름과 단언문만 읽지 않는다. 테스트 대상(SUT)의 실제 구현, 변경 요구사항, 관련 실패 경로를 함께 확인한다. PR에서는 이번 변경이 새로 만들거나 악화시킨 검증 공백을 우선한다. 테스트를 실행하지 않았다면 통과·실패했다고 말하지 않는다.

## 가치 판단 체크리스트

### 필요한 테스트인가

- [ ] 검증하려는 동작이 사용자 경험, 도메인 규칙, 데이터 보존, 경계 계약, 회귀 위험 중 무엇과 연결되는가?
- [ ] 기존 테스트와 입력·경로·기대 결과가 실질적으로 같은데 이름만 다른가?
- [ ] 중요한 실패·빈 결과·경계 값·순서 차이가 있는데 성공 사례만 반복하고 있는가?
- [ ] 단순한 언어 기능이나 구현의 한 줄을 확인하느라 유지 비용이 더 큰가?

### 실제 결함을 잡는가

- [ ] 기대 결과가 구현을 그대로 따라 계산되지 않고 요구사항이나 계약에서 독립적으로 정해졌는가?
- [ ] 핵심 동작을 잘못 바꾸면 이 테스트의 어떤 단언이 실패하는지 설명할 수 있는가?
- [ ] 결과 상태·반환값·저장 결과·외부로 전달한 값 등 관찰 가능한 효과를 확인하는가? 호출 횟수만으로 충분한 계약인지도 확인한다.
- [ ] 오류 테스트가 **어떤 오류인지** 확인하는가? `try?`, 넓은 `catch`, 단순한 “오류 발생” 검사로 다른 결함을 성공 처리하지 않는가?
- [ ] 정렬·조합·매핑을 검증한다면 입력을 바꿔도 우연히 같은 결과가 나오지 않도록 데이터가 구별되는가?

### 대상 경로를 우회하지 않는가

- [ ] 테스트가 실제로 검증하려는 프로덕션 메서드와 경계를 통과하는가?
- [ ] Mock이 테스트하려는 로직 자체를 대신 구현하고, 테스트는 Mock의 미리 정한 반환값만 확인하는가?
- [ ] 저장·마이그레이션·HTTP 인코딩처럼 경계 자체가 검증 대상인데 그 경계를 통째로 가짜로 바꾸지는 않았는가?
- [ ] 테스트만 통과시키는 전용 분기·공개 API·구현 복제가 프로덕션 코드에 들어갔는가?

### Mock과 의존성 주입이 맞는가

- [ ] 필요한 외부 의존성만 교체하고, SUT를 만들기 **전에** `withDependencies` 등으로 올바른 계약에 주입했는가?
- [ ] Mock이 실제 호출 인자·순서·횟수를 검증해야 할 계약이라면 기록하는가? 반대로 내부 호출 횟수만 과하게 고정하지는 않는가?
- [ ] 의도하지 않은 호출이 조용히 성공하는 기본 Mock 때문에 빠진 주입이나 잘못된 경로가 숨겨지지 않는가?
- [ ] Example용 `happyPath`·`emptyPath`와 테스트 데이터가 해당 사용처에 있고, Interface의 공용 계약으로 퍼지지 않았는가? 필요하면 [DI 기준](../../docs/architecture/dependency-injection.md)을 확인한다.

### 안정적이고 유지할 만한가

- [ ] 비동기 작업의 완료를 기다린 뒤 단언하는가? 고정된 `sleep`이나 실행 순서에 우연히 의존하지 않는가?
- [ ] 시간·UUID·네트워크·파일·DB 같은 변동 요인이 테스트 범위에 맞게 제어되고, 테스트끼리 상태를 공유하지 않는가?
- [ ] 준비 코드와 Mock 규모가 검증하는 판단 지점에 비례하는가? 같은 계약을 더 간단하게 검증할 수 있는가?

## 판정과 피드백

체크리스트와 `유지`, `보강`, `통합·제거 후보`, `미확인` 판정은 내부 검토에 사용한다. 결과에는 조치할 가치가 있는 Finding만 남긴다. 각 Finding에는 **검증하려는 동작, 실패 시나리오, 현재 테스트가 그 결함을 놓치는 이유, 가장 작은 보완 방법**을 적는다. 실행 없이 논리적으로 확인한 경로와 실제 실행으로 확인한 결과를 구분한다. PR 라인 코멘트는 변경 줄에 연결하고, 주변 코드가 없으면 추측으로 결론 내리지 않는다.

예를 들어 Repository 응답을 Mock으로 지정한 뒤 그 Mock의 반환값만 검사한다면 ViewModel의 상태 전이는 검증되지 않는다. 반대로 실패 응답을 주입하고 ViewModel의 오류 상태를 확인한다면 해당 전이를 검증한다.

테스트가 없다는 사실이나 낮은 커버리지 수치만으로 Finding을 만들지 않는다. 실제로 위험한 동작과 빠진 시나리오를 연결한다. 문제가 없으면 불필요한 테스트를 더 만들라고 요구하지 않는다. 사용자가 요청하지 않았다면 테스트·프로덕션 코드를 수정하거나 리뷰를 게시하지 않는다.
