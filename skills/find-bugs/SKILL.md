# Find Bugs

이 브랜치의 변경 사항을 버그·동시성 문제·레이어 경계 위반·보안 이슈 관점에서 리뷰한다.

## Phase 1: 입력 수집 (빠짐없이)

1. 전체 diff를 받는다: `git diff dev...HEAD`
2. 출력이 잘리면 변경된 파일을 하나씩 끝까지 읽는다. 일부만 보고 결론 내지 않는다.
3. 이번 브랜치에서 변경된 파일 전체 목록을 진행 전에 먼저 나열한다.

## Phase 2: 변경 파일별 위험 지점 매핑

각 변경 파일에서 다음을 식별하고 나열한다:

* 사용자 입력 지점 (SwiftUI 바인딩, TextField, 딥링크/URL 파라미터)
* 네트워크 호출 (`RemoteDataSource` → `NetworkingInterface` 경유 여부)
* 인증/토큰 처리 (Keychain 저장, 토큰 갱신, `TokenProvider`)
* 동시성 경계 (`@MainActor`, `Task`, `actor`, `Sendable`)
* 로컬 저장 (`SwiftData @Model`, `LocalDataSource`, 디스크/메모리 캐시)
* 레이어 경계를 넘는 참조 (`docs/architecture.md`의 허용 의존 표 기준)
* 외부 스트리밍 처리 (SSE 파싱, 연결 종료·재시도)

## Phase 3: 체크리스트 (모든 변경 파일에 전부 적용)

* [ ] **동시성**: UI 갱신이 `@MainActor` 밖에서 일어나지 않는가? `Task` 취소·leak, actor 재진입 문제는 없는가?
* [ ] **메모리**: 클로저의 강한 `self` 캡처로 인한 순환 참조는 없는가? `weak`/`unowned` 선택이 실제 소유 관계와 맞는가?
* [ ] **레이어 경계**: Data가 Networking 구현체를 직접 참조하거나, Domain이 Data/Core/Networking을 참조하거나, ViewModel이 네트워크·Keychain·DB를 직접 호출하지 않는가? (`docs/architecture.md` 위반)
* [ ] **인증/토큰**: 토큰이 Keychain 밖(UserDefaults, 로그, 메모리 방치)에 남지 않는가? 만료·갱신 실패 처리가 있는가?
* [ ] **로컬 저장/캐시**: SwiftData 마이그레이션이 안전한가? 캐시 무효화·용량 상한이 있는가? 동시 쓰기 경쟁은 없는가?
* [ ] **네트워크 스트리밍**: SSE 파싱 오류, 부분 응답, 연결 끊김·재시도 처리가 있는가?
* [ ] **입력 검증**: 서버 응답 디코딩 실패, force-unwrap(`!`), 배열/컬렉션 인덱스 범위 초과 가능성은 없는가?
* [ ] **상태 관리**: `Destination`/시트/알림 상태가 중복 트리거되거나 레이스 컨디션을 만들지 않는가?
* [ ] **리소스 정리**: 옵저버·구독·타이머·오디오 세션이 화면 종료 시 해제되는가?
* [ ] **정보 노출**: 에러 메시지·로그에 토큰·개인정보가 그대로 찍히지 않는가?

## Phase 4: 검증

발견한 각 이슈에 대해:

* 같은 변경 안 다른 곳에서 이미 처리되고 있지 않은지 확인한다.
* 해당 시나리오를 다루는 기존 테스트가 있는지 검색한다.
* 주변 코드를 읽어 실제 문제인지 확인한다. 짐작만으로 단정하지 않는다.

## Phase 5: 결론 전 자체 점검

결론을 내리기 전에 반드시:

1. 리뷰한 파일 전체를 나열하고 끝까지 읽었는지 확인한다.
2. 체크리스트 각 항목에 대해 문제를 찾았는지, 문제없음을 확인했는지 명시한다.
3. 확실히 검증하지 못한 영역이 있으면 그것과 이유를 남긴다.
4. 그 다음에만 최종 결과를 낸다.

## 출력 형식

**우선순위**: 보안·정확성 문제 > 버그 > 코드 품질

**건너뛰기**: 스타일·포맷 문제 (→ `swift-lint` 스킬 영역)

이슈별로:

* **파일:라인** — 한 줄 설명
* **심각도**: Critical/High/Medium/Low
* **문제**: 무엇이 잘못됐는가
* **근거**: 왜 실제 문제인가 (이미 처리되지 않음, 테스트 없음 등)
* **수정 제안**: 구체적인 방향
* **참고**: `docs/architecture.md`/`docs/swift-style.md` 해당 섹션, 또는 Apple 문서

의미 있는 문제가 없으면 없다고 말한다 — 없는 이슈를 지어내지 않는다.

**코드를 직접 고치지 않는다. 리뷰 결과만 보고한다.** 무엇을 고칠지는 사용자가 정한다.

## 트리거 케이스 vs 비-트리거 케이스

### ✅ 이 스킬을 사용한다
- "이 브랜치 버그 찾아줘", "보안 검토해줘", "이거 안전해?"
- PR 올리기 전 전체 변경분 감사

### ❌ 이 스킬을 사용하지 않는다
- 스타일/컨벤션만 궁금할 때 → `swift-lint`
- 아키텍처 배치 자체를 판단해야 할 때(새 모듈/레이어 결정) → `architecture-review`
- 승인 여부·테스트 커버리지까지 포함한 PR 종합 판단이 필요할 때 → `code-review`
