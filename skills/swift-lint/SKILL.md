# swift-lint

POSTECH Apple Developer Academy Swift Style Guide + 사용자 커스텀 룰 기반 Swift 코드 린터.

## 참조 문서

`docs/lint.md`(저장소 루트)를 Swift 일반 규칙과 필수·권장 등급의 기준으로, SwiftUI 규칙은 `docs/swift-style.md`를 기준으로 삼는다.
먼저 `docs/lint.md`의 `## 적용 및 검토 등급`을 읽고, 검토 대상에 따라 아래 섹션을 선택한다.
기존 코드의 준수 상태와 작성 정책을 구분하며, 요청 범위 밖의 기존 코드를 일괄 수정하지 않는다.

| 문서 · 섹션 | 다루는 카테고리 | 언제 읽나 |
|------|----------------|----------|
| lint.md `## 1. 네이밍` | 변수/함수/enum/struct/class/protocol/delegate 네이밍 | 거의 항상 |
| lint.md `## 2. 포맷` | 들여쓰기, 띄어쓰기, **파라미터 줄바꿈**, **import 정렬**, 주석 | 거의 항상 |
| lint.md `## 3. 코드` | 클로저, 타입 추론/어노테이션, 메모리 관리 | 함수/타입 다룰 때 |
| swift-style.md 전체 | SwiftUI View 선언 방법, 레이아웃 컨테이너 | SwiftUI 코드일 때 |

## 사용자 커스텀 룰 (강조)

파라미터 줄바꿈은 `docs/lint.md` §2.3, import 그룹·정렬은 §2.4를 따른다.
스킬에 별도 규칙을 복제하지 않고 선언·호출·이니셜라이저에 같은 문서 기준을 적용한다.

## 트리거 케이스 vs 비-트리거 케이스

### ✅ 이 스킬을 사용한다

- "이 Swift 코드 린트해줘"
- "스타일 가이드대로인지 봐줘"
- "코드 리뷰해줘" (Swift 파일 맥락에서)
- "컨벤션 체크"
- "이 함수 스타일 어때?"
- "review this Swift code"
- "lint check please"
- Swift 파일이 첨부된 상태에서 "이거 괜찮아?", "문제 있어?"

### ❌ 이 스킬을 사용하지 않는다

- "이 기능 구현해줘" → 코드 작성 작업
- "버그 고쳐줘" → 디버깅
- "성능 최적화" → 별도 분석
- "테스트 코드 짜줘" → 코드 작성
- 비-Swift 코드 검토 요청

## 작업 워크플로우 (5단계)

### 단계 1 — 검토 대상 파악

다음을 결정한다:
- 단일 파일인가, 여러 파일인가?
- 파일에 SwiftUI View가 있는가? (있으면 `docs/swift-style.md` 참고)
- 함수/메서드가 많은가? (있으면 `## 3. 코드` 섹션 참고)
- 전체 검토인가, 특정 부분만인가?

### 단계 2 — 스타일 가이드 섹션 선택적 확인

대상 코드의 성격에 따라 `docs/lint.md`(§1~§3)와 `docs/swift-style.md`(SwiftUI)에서 참고할 섹션:

| 파일 종류 | 참고할 섹션 |
|-----------|----------|
| 일반 Swift 코드 (함수/클래스/struct) | 1. 네이밍 + 2. 포맷 + 3. 코드 |
| SwiftUI View 코드 | lint.md 1. 네이밍 + 2. 포맷 + 3. 코드, swift-style.md |
| 모델/DTO만 있는 파일 | 1. 네이밍 + 2. 포맷 |
| Test 코드 | 1. 네이밍 + 2. 포맷 + 3. 코드 |

판단 어려우면 문서 전체를 읽어도 무방(하나의 파일이라 부담 적음).

### 단계 3 — 카테고리별 체크

대상 코드를 위에서 아래로 한 번 훑으면서 카테고리별 위반을 수집한다.

체크 순서:
1. **Import 섹션** — 알파벳 순서 / 중복 / 줄바꿈 위치
2. **타입 선언부** — 네이밍 (struct/class/enum/protocol)
3. **프로퍼티** — 네이밍, 타입 어노테이션, computed/observer 위치
4. **이니셜라이저** — 파라미터 줄바꿈 (커스텀 룰)
5. **함수/메서드** — 네이밍, 파라미터 줄바꿈, 클로저 사용
6. **클로저 호출** — 후행 클로저 축약, 다중 클로저 형식
7. **주석** — `///` 사용, MARK/TODO/FIXME
8. **들여쓰기/띄어쓰기** — 4 스페이스, 콜론 띄어쓰기
9. **SwiftUI 한정** — Struct로 View 선언, 레이아웃 컨테이너 1개
10. **메모리** — weak/unowned, Optional weak

각 위반은 다음 정보를 수집:
- 위치 (라인 번호 또는 함수/타입 이름)
- 현재 코드 (Bad)
- 수정 코드 (Good)
- 룰 카테고리 + 룰 이름
- 우선순위 (P0/P1/P2)

### 단계 4 — 위반 사항 보고

다음 형식으로 보고한다.

#### 보고 템플릿

```markdown
# Swift Lint 결과

**파일**: `<파일경로>`
**확인된 문제/위반**: N건 (P0: x, P1: y), **개선 제안**: P2 z건

---

## P0 — 확인된 정확성 문제

### 1. [<카테고리>] <룰 이름>
**위치**: 라인 X (또는 함수 `funcName`)

**현재 (Bad ❌)**:
\`\`\`swift
<위반 코드>
\`\`\`

**수정 (Good ✅)**:
\`\`\`swift
<수정 코드>
\`\`\`

**근거**: `docs/lint.md` §<섹션> (SwiftUI 규칙은 `docs/swift-style.md`)

---

## P1 — 필수 작성 규칙 위반
... (P0와 동일 형식)

## P2 — 권장·지양 항목 개선 제안
... (간단히 한 줄로 나열)

---

## 요약
- ✅ 잘 따르고 있는 룰: <간단히>
- ⚠️ 가장 많이 어긴 카테고리: <카테고리명>
- 💡 다음 작업 추천: <한 줄>
```

#### 우선순위 기준

등급은 `docs/lint.md`의 `## 적용 및 검토 등급`을 그대로 따른다.
네이밍·타입 어노테이션 등을 스킬 자체 판단으로 다른 등급에 재분류하지 않는다.
메모리 문제는 실제 소유 관계·수명을 확인한다. 강한 self 캡처만으로 누수를 단정하지 않는다.

### 단계 5 — 자동 수정 제안 (선택)

사용자가 "수정해줘", "고쳐줘"라고 하면:

1. **P0/P1만 자동 수정 적용**. P2는 사용자 결정.
2. 파일을 읽고 위반 사항을 한 번에 모두 수정한다.
3. 수정 전후 diff를 보여준다.
4. 사용자가 일부만 수정하길 원하면 위반 ID를 명시하게 한다 ("1번, 3번만 수정").

수정 시 주의:
- **로직 변경 절대 금지**. 스타일만.
- 변수명 바꾸면 사용처 모두 같이 바꿔야 함 (책임지고 처리).
- 의심스러우면 사용자에게 확인.

## 검토 시 자주 빠지는 함정

| 함정 | 방지법 |
|------|--------|
| Import 그룹 순서를 틀림 (Third Party를 Module보다 앞에 배치) | Apple Framework → Module(내부) → Third Party(외부) 순서를 반드시 지킨다 |
| 파라미터 줄바꿈 룰을 함수 호출에만 적용 | 함수 선언/호출/이니셜라이저 모두 동일 적용 |
| 조회 이름만 보고 API를 바꿈 | §1에 따라 기존 이름을 존중하고 `async`/`throws`로 계약을 확인한다. `fetch`를 동기 전용으로 해석하지 않는다 |
| Bool 변수 이름 검증 누락 | `isXxx`, `hasXxx`, `shouldXxx` 형태 권장 (가이드에 명시 안 됐어도 일반적) |
| weak 검토 시 모든 weak 타입을 Optional 강제 | 가이드 룰. 단 사용 맥락 본 후 제안 |
| 클로저 축약 범위를 잘못 적용 | §3의 단일·다중 후행 클로저 규칙을 따른다. 다중일 때 첫 라벨 생략과 이후 라벨 유지를 구분한다 |
| SwiftUI 룰을 UIKit 코드에 적용 | 파일 맥락 먼저 확인 |

## 사용 예시

### 예시 1 — 단일 파일 린트

**사용자**: (Settings.swift 첨부) "이 코드 린트해줘"

스킬 동작:
1. 파일을 view로 읽음.
2. SwiftUI View 있으면 `docs/swift-style.md`도 포함, 아니면 `docs/lint.md` §1/§2/§3만 참고.
3. 위에서 아래로 카테고리별 체크.
4. 위반 수집 → P0/P1/P2 분류.
5. 보고 템플릿 형식으로 결과 제시.
6. 마지막에 "수정도 적용할까요?" 한 번 물음.

### 예시 2 — 막연한 평가 요청

**사용자**: (코드 첨부) "이거 어때?"

스킬 동작:
1. Swift 코드면 린트 스킬 트리거.
2. "스타일 관점에서 검토해 드리겠습니다"라고 명시 후 진행.
3. 단계 3~4 진행.
4. 단, 위반이 0건이면 "스타일 위반은 없습니다. 다른 측면(성능/테스트성)도 봐드릴까요?" 추가.

### 예시 3 — 특정 룰만 검토

**사용자**: "Import 정렬만 봐줘"

스킬 동작:
1. `docs/lint.md` §2.4만 참고.
2. Import 섹션만 검토.
3. 다른 카테고리는 건너뜀.
4. 보고도 import 위반에 집중.

### 예시 4 — 자동 수정

**사용자**: "린트 결과 P0/P1 다 고쳐줘"

스킬 동작:
1. 직전 린트 결과 참조 (없으면 다시 린트).
2. str_replace 또는 create_file로 수정 적용.
3. 수정된 파일을 사용자에게 제시.
4. 변경 사항 요약 (어떤 카테고리에서 몇 건 수정했는지).

## 의문이 들면

`docs/lint.md`(SwiftUI는 `docs/swift-style.md`)를 다시 읽는다. 카테고리별로 잘 분리되어 있어 빠르게 찾을 수 있다.
모호한 케이스는 위반으로 단정하지 않고 미확인 사항으로 남긴다. P2는 문서의 권장·지양 항목에만 사용한다.

스타일 가이드의 목적은 **싸우지 않고 코드 읽기 좋게 하는 것**이다. 너무 엄격하게 굴어 사용자를 피곤하게 하지 말 것.
