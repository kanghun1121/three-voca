# Bad Case / Good Case

**Bad Case**는 근거가 부족하거나 현재 PR에 적용되지 않는 리뷰 지적이다. **Good Case**는 변경 전후, 실행 조건, 영향, 방어 코드 유무를 확인한 뒤 작성한 지적이다. 아래 코드는 판정 예시일 뿐이다. 실제 PR의 계약·소유 관계·서버 동작을 확인하지 않고 예시를 그대로 Finding으로 쓰지 않는다.

Finding에 필요한 최소 증거는 **변경된 코드 위치 + 도달 가능한 조건 + 그 조건의 결과**다. 실행으로 재현했다면 그 결과를, 코드 추적으로만 확인했다면 그 사실을 `근거`에서 구분한다. 추상화의 과잉처럼 실행 오류가 없는 경우에는 조건 대신 **이번 PR에서 추가된 사용 범위와 제거 시의 비용·손실**을 밝힌다. Obsidian 노트의 본문은 `변경 요약`, `Finding`, `결론`만 두고, Finding에서는 `위치`, `문제`, `발생 조건`, `영향`, `근거`, `수정 방향`을 굵은 필드 이름으로 표시한다.

## 1. 화면 이탈과 자원 수명

**Bad Case**

> [P1] AudioPlayer의 생명주기 관리가 불완전합니다.

`stop()` 호출이 안 보인다는 사실만으로는 오류가 아니다. 플레이어가 앱 전체에서 재생되도록 설계됐거나 화면 작업이 자동 취소될 수 있다.

**Good Case** — 화면 전용 재생이라는 계약, 실제 소유자, 종료 경로를 확인했을 때:

```markdown
### [P1] 화면을 닫아도 전용 음성이 계속 재생됩니다.

**위치:** AudioPlayerClient.swift:42
**문제:** 화면 종료 경로가 재생 작업을 정리하지 않음
**발생 조건:** 재생 중 화면을 pop하고 상위 Dependency가 플레이어를 계속 보유할 때
**영향:** 떠난 화면의 음성이 계속 들림
**근거:** 화면 종료 경로에 stop/cancel이 없고, 다른 소유자의 정리도 없음. 이전 구현은 종료 시 취소함. 코드 경로로 확인했고 앱에서는 실행하지 않음
**수정 방향:** 화면 전용 재생 작업을 화면 종료에 맞춰 취소
```

앱 전체 재생이 요구사항이라면 위 지적은 폐기한다.

## 2. 실패 후 재시도와 중복 부수 효과

**Bad Case** — 네트워크 요청이 있다는 이유만으로 "재시도를 추가하세요" 또는 "POST 재시도를 제거하세요"라고 쓴다. HTTP 메서드만으로 서버 멱등성이나 부수 효과를 알 수 없다.

**Good Case** — 이번 PR이 생성 요청을 자동 재시도하고, 서버가 첫 요청을 처리했지만 응답만 끊긴 경우 동일 작업을 다시 생성한다는 근거가 있을 때:

```markdown
### [P1] 응답 유실 뒤 재시도하면 학습 기록이 중복 생성됩니다.

**위치:** RetryClient.swift:42
**문제:** 동일 사용자 동작을 새 식별자로 다시 생성함
**발생 조건:** 서버가 첫 생성 요청을 저장한 직후 응답 연결이 끊겨 클라이언트가 같은 동작을 재시도할 때
**영향:** 사용자에게 동일 기록이 두 개 보임
**근거:** 새 retry 경로는 요청마다 새 식별자를 만들고, 확인한 서버 계약에는 중복 제거가 없음. 클라이언트·서버 코드 경로로 확인함
**수정 방향:** 같은 사용자 동작의 재시도에 안정된 식별자를 유지하거나 자동 재시도를 제한
```

서버가 동일 동작을 멱등 처리한다면 Finding이 아니다. 서버 계약을 읽을 수 없다면 Finding으로 단정하지 말고 필요한 계약 확인을 `결론`에 적는다.

## 3. 중간 종료와 저장 순서

**Bad Case** — 오프라인 기능이라는 이유만으로 큐·트랜잭션·복구 루틴을 모두 요구한다.

**Good Case** — PR이 동기화 커서를 데이터보다 먼저 영속화하고, 중간 종료 후 새 커서부터 재개한다면:

```markdown
### [P1] 동기화 중 종료하면 일부 기록을 영구히 건너뜁니다.

**위치:** SyncCursorStore.swift:42
**문제:** 기록 저장보다 커서를 먼저 영속화함
**발생 조건:** 새 커서 저장 후 기록 저장 전에 앱이 종료되고, 재실행 시 저장된 커서로 조회할 때
**영향:** 서버에 있는 기록 일부가 기기에 나타나지 않음
**근거:** 커서 갱신과 기록 저장이 서로 다른 단계이며 복구 시 이전 구간을 다시 읽지 않음. 코드 경로로 확인함
**수정 방향:** 기록과 커서를 함께 확정하거나, 완료 전 커서는 복구 시 재조회
```

현재 구현이 같은 트랜잭션에서 처리하거나 재실행 시 구간을 다시 읽는다면 지적하지 않는다.

## 4. SOLID, 의존 경계, 과한 설계

**Bad Case** — "구현체가 하나라 protocol은 과하다", "SOLID를 위해 UseCase가 필요하다", "화면이 하나라 Repository는 불필요하다"처럼 개수나 이름만으로 판단한다. 설계 스킬의 화면 수·개발자 수 기준을 이 저장소의 규칙처럼 적용하지 않는다.

**Good Case** — 새 계층의 실제 사용처와 저장소 규칙을 확인한 후, 이득 없이 비용만 생긴 경우:

```markdown
### [P3] 새 ForwardWordUseCase가 호출 경로만 늘립니다.

**위치:** ForwardWordUseCase.swift:18
**문제:** 새 UseCase가 Repository 호출을 그대로 전달하며 정책·조합·변환을 담당하지 않음
**발생 조건:** 이 PR의 유일한 호출부에서 사용하는 단순 조회 계약을 변경할 때 UseCase와 DI 등록도 함께 수정해야 함
**영향:** 동일한 변경의 수정 지점과 테스트 설정이 늘어남
**근거:** 기존 아키텍처 문서는 단순 조회의 Repository 직접 주입을 허용하고, 새 계층이 별도 경계를 만들지 않음. 호출부·등록·문서를 확인함
**수정 방향:** 해당 호출부에서 Repository 계약을 직접 사용
```

UseCase에 정책, 순서 보장, 모듈 경계, 안정된 계약 중 하나라도 실제로 있다면 단순 전달처럼 보여도 다시 판단한다. 반대로 계층을 줄이면 ViewModel이 HTTP·DB 구현을 직접 알아야 하는 구조가 된다면 제거를 제안하지 않는다. **제거해서 줄어드는 비용과 제거하면 잃는 이점**을 모두 설명할 수 있어야 한다.

## 5. 숫자와 규모

**Bad Case** — "timeout은 반드시 5초", "heartbeat는 20~60초", "사용자 100만 명이면 실패"처럼 외부 스킬의 숫자를 판정선으로 쓴다. 숫자의 근거가 설명되지 않았다는 사실만으로 Finding을 만들지도 않는다.

**Good Case** — PR이 도입한 timeout이 실제 정상 응답 분포보다 짧고, 정상 요청을 실패 처리하는 경로가 확인되면 해당 측정값과 실패율을 근거로 지적한다. retry가 여러 계층에서 겹친다면 실제 최대 호출 횟수를 계산해 영향과 함께 적는다. 부하·배터리·메모리 문제는 대상 기기, 호출 빈도, 측정 또는 코드상 증가 상한을 특정한다.

측정이나 정책이 없어서 영향을 판단할 수 없다면 필요한 확인을 `결론`에 적는다. 임의의 숫자로 P1/P2를 만들지 않는다.

## 6. API 호환성과 테스트

**Bad Case** — 클라이언트 PR에 enum case가 추가됐다는 이유만으로 "구버전 앱 decoding이 깨진다"고 적는다. 구버전 앱이 받는 **서버 응답**이 실제로 바뀌는지 먼저 확인해야 한다. "테스트가 부족하다"만으로도 Finding이 되지 않는다.

**Good Case** — 서버 응답 PR이 새 enum 값을 기존 앱에 전송할 수 있고, 배포된 앱의 decoder가 모르는 값을 실패 처리하며, 버전별 응답 제한이나 fallback이 없음을 확인하면 호환성 Finding으로 쓴다. 특정 실패 경로가 확인됐지만 테스트가 없다면 그 경로를 막는 회귀 테스트를 수정 방향에 포함한다.

배포된 앱의 decoder나 서버 배포 순서를 확인할 수 없다면 `결론`에 필요한 버전·계약을 남긴다. 테스트 파일이 없다는 사실을 버그의 증거로 대체하지 않는다.

## 7. 결과의 우선순위

**Bad Case** — 스타일 차이를 P1로 올리거나, 가설을 확정 버그로 쓰거나, 지적 개수를 늘리려고 같은 원인을 여러 건으로 나눈다.

**Good Case** — P1은 병합 전 해결이 필요한 데이터 유실·보안·주요 사용자 오동작, P2는 범위가 제한된 구체적 오동작 또는 의미 있는 규모 위험, P3는 확인된 유지보수 비용에 사용한다. 실제 노출 범위와 복구 가능성에 따라 조정한다. 조건과 근거가 모자란 우려는 Finding으로 만들지 않고 필요한 확인을 `결론`에 둔다. 의미 있는 Finding이 없으면 "확인한 범위에서 Finding 없음"이라고 쓴다.

## 8. Obsidian의 기존 리뷰 판정

**Bad Case** — `#152` 검색 결과가 있다는 이유로 건너뛴다. 다른 저장소의 PR이거나, 회의 노트가 PR을 언급했을 뿐일 수 있다. 반대로 head SHA가 바뀌었다는 이유로 기존 리뷰 노트를 덮어쓰는 것도 잘못이다.

**Good Case** — 노트의 `owner/repo`, PR 번호 또는 URL, 리뷰 결론·Finding 본문을 확인해 해당 PR의 **리뷰 결과**임을 판정한다. 결과가 있으면 검토한 SHA가 오래됐어도 이번 실행에서는 건너뛰고 기존 노트 위치를 보고한다. 결과가 없으면 리뷰한 뒤 PR 번호와 URL을 포함한 새 노트를 저장하고 다시 읽어 확인한다.
