# PR Review

현재 저장소의 **열린 PR 전체**를 GitHub에서 조회한다. Draft도 포함한다. Obsidian에 기존 리뷰 결과가 없는 PR만 각각 독립적으로 리뷰한다. 각 PR의 실제 base/head와 현재 head SHA를 확인하고, 그 PR의 전체 diff 및 필요한 주변 코드를 읽는다. 로컬 체크아웃의 `dev...HEAD`를 모든 PR에 재사용하지 않는다. diff가 잘리거나 파일을 읽지 못했다면 해당 PR의 검토 범위를 결론에 밝힌다.

GitHub PR 정보는 사용 가능한 GitHub 도구 또는 `gh` CLI로 읽는다. **Obsidian MCP는 중복 확인과 결과 저장에 필수**다. 이 환경의 `obsidian` MCP는 `/Users/kanghun/Documents/Obsidian Vault`만 허용하는 파일 기반 서버다. `search_files`는 파일명·경로 검색이므로, 기존 리뷰 판정에는 후보 Markdown 본문을 읽어 확인한다. 연결이나 읽기·쓰기 권한이 없으면 PR 리뷰를 시작하지 않고 원인을 보고한다. 로컬 파일이나 대화 결과를 Obsidian 저장의 대체물로 취급하지 않는다.

## Obsidian 기록 확인과 저장

1. GitHub에서 저장소의 `owner/repo`와 열린 PR 번호·URL을 확인한다. 각 PR의 diff를 읽기 **전에** Obsidian MCP로 기존 리뷰 결과를 찾는다. 저장소 이름과 PR 번호를 함께 사용해 검색하고, PR URL·문서 제목·본문의 메타데이터로 실제로 해당 PR의 **리뷰 결과**인지 확인한다. 같은 번호의 다른 저장소 노트나 PR을 단순 언급한 문서는 중복으로 보지 않는다. 검색 결과를 확인할 수 없거나 기록 여부가 모호하면 해당 PR은 리뷰하지 않고 이유를 보고한다.
2. 해당 PR의 리뷰 결과가 이미 있으면 head SHA가 달라졌더라도 이번 실행에서는 **리뷰하지 않는다**. 기존 노트를 수정하거나 새 노트를 만들지 않는다. 결과 요약에는 `기존 리뷰로 건너뜀`과 노트 위치를 적는다. 재리뷰 또는 기존 노트의 형식 변경은 사용자가 명시적으로 요청했을 때만 한다.
3. 새 PR의 리뷰를 마치면 결과 전체를 Obsidian MCP로 저장한다. 기존 PR 리뷰 노트 위치가 있으면 따른다. 없으면 `PR Reviews/<owner>/<repo>/PR-<number>.md` 형식을 사용한다. 제목과 최소 메타데이터에 `owner/repo`, PR 번호·URL, 검토한 head SHA를 넣어 중복 판정에 사용한다. 본문은 아래의 세 섹션만 쓴다. Finding이 없어도 결과 노트를 저장한다.
4. 저장 직전 같은 PR의 결과가 새로 생기지 않았는지 다시 확인한다. 기존 노트를 덮어쓰지 않는다. 저장 후 노트를 다시 읽어 PR 식별자와 결과가 기록됐는지 확인한다. 저장이 실패하거나 성공 여부가 불명확하면 재조회한 뒤 처리하고, 확인되지 않은 결과를 `저장 완료`라고 보고하지 않는다. 저장 문제가 해결되지 않으면 다음 PR로 넘어가기 전에 중단하고 미저장 결과를 보고한다.

Obsidian MCP에서 해당 변경에 관련된 요구사항, ADR, 아키텍처 결정, 운영 메모도 찾아 근거로 사용한다. 관련 문서를 찾지 못하면 없는 규칙을 추정하지 않는다. 저장소 규칙과 Obsidian 문서가 충돌하면 문서의 적용 범위와 시점을 확인하고, 해결되지 않은 충돌은 출처와 함께 밝힌다.

## 리뷰 관점

PR의 목적과 기존 코드베이스를 확인한 다음 아래 네 관점만 적용한다. 해당하지 않는 질문은 건너뛴다.

1. **동작과 실패 경로** — 정확성, 회귀, 데이터·보안 영향. 변경된 동작에서 실패, 취소, 중복 실행, 비동기 완료 순서 변경, 화면 이탈, background/termination, retry, partial success가 실제로 문제가 되는지 확인한다. 저장·동기화가 바뀌면 중간 종료 때 데이터와 진행 위치가 어긋나는지도 본다.
2. **경계와 복잡도** — SOLID, 모듈 의존 방향, 책임 배치, 과한 설계. 새 추상화가 의존 경계, 테스트 대체, 비즈니스 규칙, 재사용 중 무엇을 실제로 얻는지 확인한다. 반대로 필요한 책임이 UI나 호출부에 흩어졌는지도 본다. 기존 아키텍처 규칙과 PR의 요구사항을 기준으로 판단한다.
3. **검증과 호환성** — 변경된 핵심 동작을 검증하는 테스트, 기존 소비자·저장 데이터·API 계약·마이그레이션 영향을 확인한다. 테스트 부재 자체보다 검증되지 않은 구체적 위험과 배포된 버전의 실제 소비 경로를 본다.
4. **운영 영향** — 해당 변경에 한해 성능·자원 수명·관측성·복구 가능성을 확인한다. retry 횟수, timeout, debounce, cache 크기, heartbeat 같은 새 판단선은 요구사항·측정·기존 정책 중 어떤 근거로 정했는지 살핀다. 근거 부재만으로 Finding을 만들지 않고, 가능한 오동작이나 비용을 확인한다. 첨부한 설계 스킬의 화면 수·초·횟수 기준을 이 PR의 규칙으로 가져오지 않는다.

## Finding 검증

확정적인 Finding을 쓰기 전 다음을 모두 확인한다.

- 이번 PR이 새로 만들었거나 악화시킨 문제인가?
- 실제로 실행 가능한 경로와 **발생 조건**을 설명할 수 있는가?
- 그 조건에서 어떤 영향이 생기는가?
- 변경 코드와 주변 코드, 테스트, 문서 중 무엇이 판단을 뒷받침하는가? 다른 경로에서 이미 처리하지 않는가? 변경 전에는 같은 문제가 없었는가?
- 사용자 영향 또는 구체적인 유지보수 비용에 비추어 수정할 가치가 있는가?

발생 조건은 반드시 적되, 실제 실행으로 재현한 경우와 코드 경로만 확인한 경우를 구분한다. 실행하지 않은 시나리오를 "재현됨"이라고 쓰지 않는다. 조건이나 근거가 부족하면 Finding으로 단정하지 말고 필요한 확인을 `결론`에 간결하게 적는다. 특히 과한 설계는 "계층이 많다"만으로 지적하지 않는다. 해당 구조를 제거할 때 잃는 이점과 제거해서 줄어드는 비용을 함께 설명할 수 있어야 한다. 스타일과 개인 취향은 Finding으로 만들지 않는다. [Bad Case / Good Case](references/bad-good-cases.md)를 판정과 작성에 참고한다.

## 우선순위와 결과

데이터 유실, 보안 노출, 사용자에게 보이는 오동작·회귀, 규모 문제, 유지보수 비용 순으로 영향을 평가한다. 심각도는 발생 가능성·영향 범위·복구 가능성을 함께 고려하며, 이 순서를 기계적인 등급표로 쓰지 않는다. 중복 Finding은 합치고, 영향이 큰 순서로 제시한다.

새로 리뷰한 PR 노트의 본문은 **`변경 요약`, `Finding`, `결론` 세 섹션만** 둔다. PR 식별에 필요한 번호·URL·검토 SHA는 제목과 최소 메타데이터에 보관한다. base/head, Draft, CI 및 검증 범위는 리뷰 중 확인하되 별도 섹션이나 목록을 만들지 않는다. 결론은 `승인 가능 / 수정 필요 / 사람 판단 필요` 중 하나와 필요한 짧은 이유를 적는다. Finding이 없으면 `확인한 범위에서 Finding 없음`이라고 적는다.

각 Finding은 아래 여섯 필드만 사용하고 **필드 이름을 굵게** 표시한다. 위치에는 가능하면 PR의 코드 링크와 줄 번호를 넣는다. 실제 실행 여부가 판단에 중요하면 `근거`에서 코드 확인과 실행 검증을 구분한다.

```markdown
### [P1/P2/P3] 영향이 드러나는 제목

**위치:** 파일:라인
**문제:** 잘못된 동작 또는 불필요한 구조
**발생 조건:** 상태와 실행 순서, 또는 과한 구조가 사용되는 범위
**영향:** 사용자·시스템 또는 유지보수 비용
**근거:** PR 코드와 관련 계약·문서·테스트
**수정 방향:** 문제를 없애는 가장 작은 변경
```

PR 사이의 의존 관계나 같은 코드 충돌은 각 PR의 결론을 섞지 말고 별도 `PR 간 관계`로 보고한다. 대화에는 새로 저장한 결과와 건너뛴 PR을 노트 링크와 함께 요약한다. PR 코멘트 게시·승인·변경 요청·코드 수정은 별도 요청이 있을 때만 수행한다.
