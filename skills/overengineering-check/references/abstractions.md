# OEC-ABSTRACT: 계층과 추상화

적용: UseCase, Repository, DataSource, 래퍼, 프로토콜, 전략, 팩토리, 공개 옵션 또는 공통 기반이 추가·확장된 경우.

- [ ] 새 UseCase가 Repository 호출을 전달하기만 하고 도메인 규칙·호출 조합·순서 관리를 하지 않는가?
- [ ] 새 래퍼나 전략이 변환·정책·의존 경계 없이 기존 동작을 다른 파일로 옮기는가?
- [ ] 실제 구현과 호출 방식은 하나인데 미래의 교체 가능성을 위한 설정·프로토콜·팩토리·분기가 추가됐는가?
- [ ] 변경 이유가 다른 기능을 공통 기반에 묶어 각 호출부의 조건이 늘었는가?

계약이 테스트 대체, 모듈 경계 또는 실제 호출자 분리에 쓰이면 그 이점을 먼저 확인한다. 이 프로젝트의 Repository 계약과 Interface 분리는 소비자 수나 파일 수만으로 제거 후보가 되지 않는다. 더 작은 구조가 현재 필요한 의존 경계를 훼손한다면 제안하지 않는다.
