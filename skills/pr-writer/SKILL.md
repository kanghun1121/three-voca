# PR Writer

나중에 나 자신이 다시 읽을 PR을 쓴다. 근거 없는 내용을 지어내지 않고, 확인된 사실만 담는다.

## 요청 범위와 근거

- 본문 작성·다듬기 요청이면 제목과 본문만 준비한다. 생성·업데이트 요청이면 원격 작업
  (`gh pr create`/`gh pr edit`)까지 수행한다. 상태 조회나 ready 전환 요청에 불필요한 본문
  재작성을 끼워 넣지 않는다.
- `.github/PULL_REQUEST_TEMPLATE.md`를 확인한다 — 이 저장소는 이게 유일한 PR 본문 구조다.
  필수 섹션(연관 이슈/작업 내용)은 유지하고, 스크린샷처럼 선택 섹션은 필요할 때만 채운다.
- 브랜치, 작업 트리, 기존 PR, base/head, 커밋 범위, 전체 diff를 확인한다:

  ```bash
  git branch --show-current
  git status --porcelain
  gh pr view --json number,title,body,url,baseRefName,headRefName 2>/dev/null
  ```

  기존 PR이 있으면 그 `baseRefName`을 쓴다. 없으면 `dev`(이 저장소의 확인된 통합 브랜치)를 쓴다 —
  다만 매번 추측으로 단정하지 말고 기존 PR 또는 `gh repo view --json defaultBranchRef`로 재확인한다.
- `git log BASE..HEAD`, `git diff --stat BASE...HEAD`, `git diff BASE...HEAD`로 전체 범위를 읽는다
  (`BASE`는 위에서 확인한 실제 ref). 파일 목록과 커밋 메시지만으로 본문을 쓰지 않는다. 기존 원격
  PR을 다룰 땐 로컬 HEAD와 원격 head의 차이도 확인한다.
- 커밋되지 않은 변경과 PR에 포함되는 변경을 구분한다. 본문 작성을 이유로 사용자의 파일을 커밋하거나
  정리하지 않는다.
- 붙여 넣은 본문만 주어졌으면 그 범위 안에서 편집한다. diff·테스트 결과·배경이 없으면 지어내지
  않는다. 핵심 의미가 모호할 때만 필요한 질문을 한다.
- `dev`에 그대로 있다면 먼저 `create-branch`로 브랜치를 만들고 진행한다.

## 내용 선별

작성 전에 변경 목적, 전후 동작, 중요한 구현 선택, 검증 결과, 남은 제약을 근거와 대조한다.
이 작업용 메모를 본문에 그대로 옮기지 않는다.

- 첫 불릿(또는 첫 문단)에서 어떤 상황이 왜 달라지는지 설명한다. 원인·선택 이유는 코드·이슈·사용자
  설명으로 확인된 범위에서만 쓴다.
- 파일별로 나열하지 않고 하나의 동작·목적에 속하는 변경을 묶는다. 파일·함수 이름은 리뷰 위치나
  설계 결정을 설명하는 데 필요할 때만 쓴다.
- 독립적인 목적이 여러 개 섞였으면 각각 드러내고 분리 후보를 알린다. 본문만으로 단일 목적처럼
  포장하거나 브랜치를 임의로 분리하지 않는다.
- 최종 변경 상태를 설명한다. 중간 시도·작업 순서·대화 이력은 설계 판단에 필요한 경우 외엔 덜어낸다.
- 테스트 코드 추가, 실제 실행, 통과 결과를 구별한다. 수행하지 않은 수동 확인이나 확인하지 않은
  CI 결과를 성공으로 쓰지 않는다.
- API 호환성, 마이그레이션, 배포 순서, 데이터 손실 등 확인된 중요 사항은 분량을 줄이더라도 유지한다.
  근거 없는 위험 목록을 추가하지 않는다.
- 이슈를 완전히 닫는 변경인지, 일부만 다루는지 구분한다. 일부만 다루면 "작업 내용"에 그 사실을 남긴다.

## 제목과 본문

### 제목 — 저장소 규칙을 따른다

```
[T-<issue-number>] [<Type>] <설명>
```

- `<issue-number>`는 브랜치명(`<issue>-<type>-<kebab>`)에서 추출한다. 이미 PR이 있으면 기존
  제목의 이슈 번호를 유지한다.
- `<Type>`은 `create-branch`가 쓰는 5개(Feature/Fix/Refactor/Chore/Docs) 중 브랜치명의 타입을
  그대로 쓴다.
- `<설명>`은 한국어로, 브랜치 전체 diff가 다루는 가장 지배적인 변경을 구체적으로 가리켜야 한다.
  "업데이트", "정리", "수정 사항" 같은 모호한 표현을 쓰지 않는다.
- 기존 제목이 지금 diff 전체를 여전히 설명하면 그대로 둔다.

예: `[T-133] [Refactor] 청크 리더 화면 리컬러링`

### 본문 — 이 저장소는 구조를 고정한다

변경 복잡도에 따라 구조를 골라 쓰지 않는다. `.github/PULL_REQUEST_TEMPLATE.md` 구조를 항상
그대로 쓴다:

```markdown
## 연관 이슈

<#이슈번호>

## 📝 작업 내용

- <바뀐 동작을 구체적으로, 항목당 한 줄. 파일별이 아니라 목적별로 묶는다>

## 🖼️ 스크린샷 (선택)

<확인한 기기/시뮬레이터와 방법. 실제 이미지가 없으면 검증 방법만 텍스트로 남긴다>
```

- 필수 섹션(연관 이슈/작업 내용)은 항상 채운다. 스크린샷은 선택이지만 헤더 자체는 템플릿대로
  유지하고, 시각적 변경이 없으면 검증 방법(시뮬레이터 확인 등)으로 대체한다.
- 템플릿에 없는 섹션(체크리스트, 리뷰 포인트, Test Plan, 라벨 안내)을 습관적으로 추가하지 않는다.
- 커밋 로그·CI 로그·검증 명령 출력·파일 전체 목록을 그대로 붙이지 않는다. 재현에 필요한 명령만
  남긴다.
- 고객명·이메일·시크릿·PII를 넣지 않는다.
- 이슈 참조는 사용자 입력·브랜치명·커밋에서 확인된 것만 쓴다.

## 자연스러운 문장

문체나 분량 판단이 어려우면 [references/examples.md](references/examples.md)의 예시를 참고한다.

- 이 저장소의 실제 "작업 내용" 불릿은 완결된 문장이 아니라 **짧은 명사형/동사 종결 어구**다
  (예: "청크 박스 배경을 상시 연한 블루로 변경", "단어 목록 두 번째 배지 제거"). 이 스타일을
  유지한다. "~했습니다" 식 완결 문장으로 부풀리지 않는다.
- "안정성을 개선했습니다", "사용자 경험을 향상했습니다", "효율적으로 처리합니다" 같은 표현은
  실제로 달라진 동작으로 바꾼다. 측정하지 않은 성능 향상을 주장하지 않는다.
- 같은 내용을 여러 불릿에서 반복하지 않는다. 불릿마다 새로운 정보를 담는다.
- 습관적인 굵은 글씨, 장식 이모지(템플릿에 이미 있는 것 제외), 깊은 중첩 목록을 피한다. 비교는
  표가 더 명확할 때만 표로 쓴다.
- 사람처럼 보이게 하려고 감정·개인 경험·고민 과정·구어체를 넣지 않는다. 자연스러움은 정확한
  상황과 구체적인 동사에서 나온다.
- "아래는 작성한 PR입니다", 작업 과정 서술, 자기 평가, 마무리 인사 같은 대화용 문구를 PR 본문에
  넣지 않는다.

## 최종 편집

내보내기 전에 제목과 본문을 전체 변경 및 확보한 근거와 대조한다.

1. 처음 읽는 사람(미래의 나 포함)이 변경 이유와 결과를 알 수 있는가?
2. 각 항목에 근거가 있고, 테스트 추가와 실행 결과가 구별되는가?
3. 같은 사실을 반복하거나 diff를 문장으로 옮긴 부분을 덜어낼 수 있는가?
4. 중요한 제약·호환성·실패가 짧게 쓰는 과정에서 사라지지 않았는가?
5. 템플릿의 필수 항목과 실제 이슈 번호가 보존되었는가?

형식만 다듬지 말고 겹치는 문단은 다시 쓴다. 작성만 요청받았으면 제목과 완성된 본문을 반환하고
작업용 체크리스트를 붙이지 않는다.

## 생성·업데이트

- 이미 허용된 범위에서 브랜치를 push하고 `gh pr create` 또는 `gh pr edit`를 쓴다. draft/ready는
  사용자 요청을 따른다 — 기본은 draft.
- 여러 줄 본문은 세션 스크래치패드 디렉터리의 임시 Markdown 파일에 정확한 줄바꿈으로 저장하고
  `--body-file`로 전달한다. 커밋 메시지를 그대로 채우는 `--fill`을 기본값으로 쓰지 않는다.

  ```bash
  gh pr create --draft --title '<title>' --body-file <스크래치패드>/pr-body.md
  gh pr edit <number> --title '<title>' --body-file <스크래치패드>/pr-body.md
  ```

- 이슈·리뷰어·레이블은 확인된 정보만 쓴다.
- 생성·편집 뒤 `gh pr view`로 제목, 본문, base/head, draft 상태를 확인한다. 실패하거나 결과가
  불명확하면 조회 후 재시도해 중복 PR 생성을 피한다.
- ready 전환에 필요한 검증(CLAUDE.md의 검증 절차 등)이 있으면 수행하거나 결과를 확인한다.
  제목·본문 편집만으로 테스트를 실행했다고 보고하지 않는다.
- 결과는 PR URL과 함께 반환한다.
- 후속 커밋이 범위·접근·리스크를 실제로 바꿀 때만 제목/본문을 새로 쓴다. 오타·포맷·이름만 바뀐
  후속 커밋은 건너뛴다. 갱신할 땐 리뷰 이력을 서술하지 말고 지금 전체 diff 기준으로 다시 쓴다.

## 참고

- 이 스킬은 `.claude/commands/git/pr.md`(구 `/git:pr` 커맨드)를 대체한다. 라벨/리뷰어 자동 할당,
  Jira/Linear 연동, 배치 작업, 분석 리포트 등 이 저장소에 없는 인프라 언급은 들어냈다.
- 본문 구조·톤은 유연하게 고르는 방식 대신, 이 저장소의 고정 템플릿과 실제 최근 PR(`gh pr list`)
  스타일을 기준으로 삼는다.
