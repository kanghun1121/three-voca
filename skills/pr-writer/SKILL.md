# PR Writer

나중에 나 자신이 다시 읽을 PR을 쓴다. 근거 없는 내용을 지어내지 않고, 확인된 사실만 담는다.

## PR 원칙

- **Single Purpose** — 한 PR이 하나의 구체적인 기능 또는 문제를 다루도록 범위를 판단한다.
- **Small & Focused** — 목적이 하나여도 리뷰어가 전체 변경을 한 번에 이해하기 어렵다면 독립적으로
  검토·revert할 수 있는 단위로 나눌 후보를 알린다.
- **What + Why** — 달라진 동작과 그 변경이 필요한 확인된 문제·사용자 영향·시나리오를 함께 전한다.
- **Not How** — 코드에서 바로 읽히는 구현 세부사항을 본문에 반복하지 않는다.
- **Reviewer-oriented Structure** — 파일·커밋 순서가 아닌 기능·문제·개념별로 묶어 중요한 변경부터 보여준다.
- **Evidence** — 테스트 실행, 수동 확인, 스크린샷처럼 실제 확인한 근거를 결과와 구분해 남긴다.
- **Historical Value** — 몇 달 뒤에도 변경이 존재하는 이유를 알 수 있도록 당시 해결한 문제나
  지원하려던 시나리오를 짧게 보존한다.

## 요청 범위와 근거

- 본문 작성·다듬기 요청이면 제목과 본문만 준비한다. 생성·업데이트 요청이면 원격 작업
  (`gh pr create`/`gh pr edit`)까지 수행한다. 상태 조회나 ready 전환 요청에 불필요한 본문
  재작성을 끼워 넣지 않는다.
- `.github/PULL_REQUEST_TEMPLATE.md`를 확인한다 — 이 저장소는 이게 유일한 PR 본문 구조다.
  필수 섹션(연관 이슈/작업 내용)은 유지하고, 스크린샷처럼 선택 섹션은 필요할 때만 채운다.
- 브랜치, 작업 트리, 기존 PR, base/head, 커밋 범위, 전체 diff를 확인한다:

  ```bash
  git branch --show-current
  git status --porcelain
  gh pr view --json number,title,body,url,baseRefName,headRefName 2>/dev/null
  ```

  기존 PR이 있으면 그 `baseRefName`을 쓴다. 없으면 `dev`(이 저장소의 확인된 통합 브랜치)를 쓴다 —
  다만 매번 추측으로 단정하지 말고 기존 PR 또는 `gh repo view --json defaultBranchRef`로 재확인한다.
- `git log BASE..HEAD`, `git diff --stat BASE...HEAD`, `git diff BASE...HEAD`로 전체 범위를 읽는다
  (`BASE`는 위에서 확인한 실제 ref). 파일 목록과 커밋 메시지만으로 본문을 쓰지 않는다. 기존 원격
  PR을 다룰 땐 로컬 HEAD와 원격 head의 차이도 확인한다.
- 커밋되지 않은 변경과 PR에 포함되는 변경을 구분한다. 본문 작성을 이유로 사용자의 파일을 커밋하거나
  정리하지 않는다.
- 붙여 넣은 본문만 주어졌으면 그 범위 안에서 편집한다. diff·테스트 결과·배경이 없으면 지어내지
  않는다. 핵심 의미가 모호할 때만 필요한 질문을 한다.
- `dev`에 그대로 있다면 먼저 `create-branch`로 브랜치를 만들고 진행한다.

## 분석 → 그룹화 → 우선순위 → 압축 → 작성

전체 diff를 읽은 뒤 본문보다 먼저 작업용 메모를 만든다. 메모에는 `Primary Change`(PR을 한 문장으로
설명할 지배적인 변경), `Change Groups`(같은 사용자 동작·문제·화면 흐름에 속하는 변경),
`Verification`(테스트 코드 변경과 실제 실행·성공 결과), `Independent Changes`(별도 PR 후보)를
구분한다. 메모를 PR 본문에 그대로 옮기지 않는다.

- 파일·커밋 순서 대신 변경 목적에 따라 묶는다. 함께 revert하는 것이 자연스러운 변경도 같은 그룹의
  근거다. 작은 구현 변경 여러 개가 하나의 동작을 만들면 한 불릿으로 압축한다.
- 목적이 하나이고 핵심 항목이 2~4개로 강하게 연결되면 평평한 불릿을 쓴다. 기능 영역이 둘 이상이거나,
  항목이 6개 이상이거나, 기능·버그·Example/Mock·개발 도구가 섞이면 그룹화를 우선한다. 그룹은
  보통 3~5개 이내로 합치고, 기능·화면 흐름·변경 목적의 이름을 쓴다. PR 자체가 아키텍처나 테스트
  인프라 변경인 경우에만 기술 계층을 그룹 이름으로 쓸 수 있다.
- 첫 항목 또는 첫 그룹에 Primary Change를 둔다. 이어서 사용자 동작, 버그 수정, 제거된 동작,
  Example/Mock, 개발 도구 순으로 리뷰 중요도를 판단하고, 실제 검증 결과는 마지막에 둔다. Primary
  Change가 Example이나 도구라면 그것을 먼저 둔다. diff의 등장 순서를 따르지 않는다.
- 무엇이 달라졌는지를 먼저 쓴다. 변수·프로퍼티·함수 이동·파일 위치 등 내부 구현은 리뷰에 필요할
  때만 남긴다. Public API, 데이터 모델·저장 방식, 네트워크 계약, 아키텍처 의존성, 마이그레이션,
  호환성 변경은 구현 방식 자체가 중요한 정보일 수 있다.
- Example/Mock은 개별 값보다 리뷰에 의미 있는 상태·시나리오 차이로 압축한다. 특정 값이 테스트
  케이스의 핵심이면 짧게 남긴다. 삭제된 기능과 관련 테스트 삭제는 연결해 설명하되, 테스트 삭제가
  회귀 위험을 만들면 별도 항목으로 드러낸다.
- 검증 결과가 있으면 `작업 내용`의 마지막 `**검증**` 그룹에 실제 실행한 테스트·빌드·화면 확인을
  적을 수 있다. 테스트 코드 추가·수정은 해당 기능 그룹의 구현 변경이고, 테스트 실행·성공은 별개다.
  실행 기록이 없으면 통과했다고 쓰지 않는다.
- 하나의 기능·문제인지, 함께 revert할지, 같은 리뷰어가 함께 검토할지, 구체적인 제목 하나로 설명할
  수 있는지 확인한다. 둘 이상에 `아니다`면 별도 PR 후보로 본다. 목적이 같더라도 변경 범위가 한 번에
  검토하기 어렵다면 독립적으로 검토할 수 있는 흐름을 분리 후보로 본다. 브랜치·커밋을 자동 분리하지 않는다.
  생성 요청이라면 생성 전에 사용자에게 짧게 알리고, 본문 작성 요청이면 본문 밖에서 알린다.

규모에 맞는 구조·압축 수준은 [references/examples.md](references/examples.md)를 참고한다. 문장을
복사하지 않는다.

## 내용 선별

- 바뀐 동작과 그것이 필요한 이유를 쓴다. 이유는 확인된 문제 현상, 사용자 영향, 재현·검증해야 할
  시나리오로 짧게 전한다. 같은 이유를 모든 불릿에 반복하지 않는다. 구현 방식의 선택 과정·대안 비교·
  트레이드오프는 리뷰에 꼭 필요한 경우 외에는 이슈나 커밋 메시지에 남긴다.
- 첫 불릿(또는 첫 문단)에서 어떤 동작이 달라지는지 설명한다. 고친 문제의 현상은 코드·이슈·사용자
  설명으로 확인된 범위에서만 쓴다.
- 최종 변경 상태를 설명한다. 중간 시도·작업 순서·대화 이력은 덜어낸다.
- 수행하지 않은 수동 확인이나 확인하지 않은 CI 결과를 성공으로 쓰지 않는다.
- API 호환성, 마이그레이션, 배포 순서, 데이터 손실 등 확인된 중요 사항은 분량을 줄이더라도 유지한다.
  근거 없는 위험 목록을 추가하지 않는다.
- 이슈를 완전히 닫는 변경인지, 일부만 다루는지 구분한다. 일부만 다루면 "작업 내용"에 그 사실을 남긴다.

## 제목과 본문

### 제목 — 저장소 규칙을 따른다

```
[T-<issue-number>] [<Type>] <설명>
```

- `<issue-number>`는 브랜치명(`<issue>-<type>-<kebab>`)에서 추출한다. 이미 PR이 있으면 기존
  제목의 이슈 번호를 유지한다.
- `<Type>`은 `create-branch`가 쓰는 5개(Feature/Fix/Refactor/Chore/Docs) 중 브랜치명의 타입을
  그대로 쓴다.
- `<설명>`은 한국어로, Primary Change의 구체적인 기능·문제를 가리켜야 한다. "업데이트", "정리",
  "수정 사항" 같은 모호한 표현을 쓰지 않는다. 하나의 제목으로 전체 변경을 설명하기 어렵다면 PR
  범위를 다시 확인한다.
- 기존 제목이 지금 diff 전체를 여전히 설명하면 그대로 둔다.

예: `[T-133] [Refactor] 청크 리더 화면 리컬러링`

### 본문 — 이 저장소는 구조를 고정한다

`.github/PULL_REQUEST_TEMPLATE.md`의 섹션 구조는 항상 그대로 쓴다. `작업 내용` 안에서는 변경
규모에 따라 평평한 불릿 또는 1단계 소그룹을 고른다:

```markdown
## 연관 이슈

<#이슈번호>

## 📝 작업 내용

- <바뀐 동작을 목적별로 압축한 불릿>

## 🖼️ 스크린샷 (선택)

<UI 변경의 실제 이미지 또는 직접 확인한 화면. 시각적 변경이 없으면 - 없음>
```

- 필수 섹션(연관 이슈/작업 내용)은 항상 채운다. 스크린샷 헤더도 템플릿대로 유지한다. UI 변경의
  이미지가 있으면 사용하고, 이미지 없이 직접 화면을 확인했다면 그 화면을 짧게 적는다. 시각적 변경이
  없으면 `- 없음`으로 남길 수 있다. Unit Test·CI·빌드 결과는 이 섹션에 넣지 않는다.
- 템플릿에 없는 섹션(체크리스트, 리뷰 포인트, Test Plan, 라벨 안내)을 습관적으로 추가하지 않는다.
- 커밋 로그·CI 로그·검증 명령 출력·파일 전체 목록을 그대로 붙이지 않는다. 재현에 필요한 명령만
  남긴다.
- 고객명·이메일·시크릿·PII를 넣지 않는다.
- 이슈 참조는 사용자 입력·브랜치명·커밋에서 확인된 것만 쓴다.

## 자연스러운 문장

문체나 분량 판단이 어려우면 [references/examples.md](references/examples.md)의 비슷한 규모 예시를 참고한다.

- 이 저장소의 실제 "작업 내용" 불릿은 완결된 문장이 아니라 **짧은 명사형/동사 종결 어구**다
  (예: "청크 박스 배경을 상시 연한 블루로 변경", "단어 목록 두 번째 배지 제거"). 이 스타일을
  유지한다. "~했습니다" 식 완결 문장으로 부풀리지 않는다.
- "안정성을 개선했습니다", "사용자 경험을 향상했습니다", "효율적으로 처리합니다" 같은 표현은
  실제로 달라진 동작으로 바꾼다. 측정하지 않은 성능 향상을 주장하지 않는다.
- 같은 내용을 여러 불릿에서 반복하지 않는다. 불릿마다 새로운 정보를 담는다.
- 굵은 글씨는 복잡한 PR의 1단계 그룹 제목에만 쓴다. 장식 이모지(템플릿에 이미 있는 것 제외)와
  3단계 이상 중첩 목록을 피한다. 비교는 표가 더 명확할 때만 표로 쓴다.
- 사람처럼 보이게 하려고 감정·개인 경험·고민 과정·구어체를 넣지 않는다. 자연스러움은 정확한
  상황과 구체적인 동사에서 나온다.
- "아래는 작성한 PR입니다", 작업 과정 서술, 자기 평가, 마무리 인사 같은 대화용 문구를 PR 본문에
  넣지 않는다.

## 최종 편집

내보내기 전에 제목과 본문을 전체 변경 및 확보한 근거와 대조한다.

1. 처음 읽는 사람과 몇 달 뒤의 내가 무엇이 왜 바뀌었는지 알 수 있는가? 확인되지 않은 이유나 불필요한
   구현 선택 과정이 섞이지 않았는가?
2. 각 항목에 근거가 있고, 테스트 추가와 실행 결과가 구별되는가?
3. 파일·diff 순서의 changelog가 되었거나 같은 목적이 여러 불릿에 흩어지지 않았는가?
4. 첫 3~5개 항목으로 핵심을 알 수 있는가? 구현 상세보다 바뀐 동작을 설명하는가?
5. Example/Mock의 개별 값을 과하게 나열하거나 그룹을 너무 잘게 나누지 않았는가?
6. 독립 변경이 섞였는가? 목적이 하나여도 리뷰 범위가 너무 넓지 않은가? 하나의 구체적인 제목으로
   전체를 설명할 수 있는가?
7. 중요한 제약·호환성·실패가 압축 과정에서 사라지지 않았는가?
8. 템플릿의 필수 항목과 실제 이슈 번호가 보존되었는가? 검증 결과가 스크린샷 섹션에 섞이지 않았는가?

문제가 있으면 문장만 다듬지 말고 구조를 다시 쓴다. 작성만 요청받았으면 제목과 완성된 본문을 반환하고
작업용 체크리스트를 붙이지 않는다.

## 생성·업데이트

- 이미 허용된 범위에서 브랜치를 push하고 `gh pr create` 또는 `gh pr edit`를 쓴다. draft/ready는
  사용자 요청을 따른다 — 기본은 draft.
- 여러 줄 본문은 세션 스크래치패드 디렉터리의 임시 Markdown 파일에 정확한 줄바꿈으로 저장하고
  `--body-file`로 전달한다. 커밋 메시지를 그대로 채우는 `--fill`을 기본값으로 쓰지 않는다.

  ```bash
  gh pr create --draft --title '<title>' --body-file <스크래치패드>/pr-body.md
  gh pr edit <number> --title '<title>' --body-file <스크래치패드>/pr-body.md
  ```

- 이슈·리뷰어·레이블은 확인된 정보만 쓴다.
- 생성·편집 뒤 `gh pr view`로 제목, 본문, base/head, draft 상태를 확인한다. 실패하거나 결과가
  불명확하면 조회 후 재시도해 중복 PR 생성을 피한다.
- ready 전환에 필요한 검증(CLAUDE.md의 검증 절차 등)이 있으면 수행하거나 결과를 확인한다.
  제목·본문 편집만으로 테스트를 실행했다고 보고하지 않는다.
- 결과는 PR URL과 함께 반환한다.
- 후속 커밋이 범위·접근·리스크를 실제로 바꿀 때만 제목/본문을 새로 쓴다. 오타·포맷·이름만 바뀐
  후속 커밋은 건너뛴다. 갱신할 땐 리뷰 이력을 서술하지 말고 지금 전체 diff 기준으로 다시 쓴다.

## 참고

- 이 스킬은 `.claude/commands/git/pr.md`(구 `/git:pr` 커맨드)를 대체한다. 라벨/리뷰어 자동 할당,
  Jira/Linear 연동, 배치 작업, 분석 리포트 등 이 저장소에 없는 인프라 언급은 들어냈다.
- 본문 구조·톤은 유연하게 고르는 방식 대신, 이 저장소의 고정 템플릿과 실제 최근 PR(`gh pr list`)
  스타일을 기준으로 삼는다.
